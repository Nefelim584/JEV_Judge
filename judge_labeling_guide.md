# Гайд разметки тестового набора судьи

> Статус: черновик. Правила совпадают с `dataset_dicr.md` §8, чтобы человеческие метки и синтетика означали одно и то же.
> Тестовый набор строится из реальных троек нашей системы (вопрос, найденные чанки, ответ), замораживается и **никогда не используется для обучения** (`todo.md`, 2.13).

---

## 1. Что размечается

Каждый пример — один ответ ассистента. Разметчик видит вопрос пользователя, найденные чанки (обычно 4, с номерами `[1]…[4]`) и ответ, **уже разбитый на предложения** тем же сплиттером, что использует судья.

| Уровень | Поле | Значения |
|---|---|---|
| Предложение | `is_factual` | да / нет (раздел 3) |
| Предложение (если фактическое) | `status` | `supported` / `supported_multi` / `contradicted` / `not_mentioned` (раздел 4) |
| Предложение | `chunks` | номера чанков, которые поддерживают предложение (для `supported`, `supported_multi`) или противоречат ему (для `contradicted`) |
| Ответ | `relevance` | 4 уровня (раздел 5) или «полный отказ» |
| Ответ | `answerable` | да / частично / нет: есть ли в чанках ответ на вопрос (раздел 6) |
| Любой уровень | `unsure` | флажок «не уверен» и короткий комментарий |

Метка ответа «faithful» **не размечается**, а вычисляется: ответ faithful, если все фактические предложения имеют статус `supported` или `supported_multi`.

Метки по каждой паре (предложение, чанк) выводятся из `status` и `chunks`. Чанки из списка получают `supports` или `contradicts`, остальные — `silent`. Так разметчику не нужно делать 20 отдельных суждений на ответ.

---

## 2. Главный принцип

**Судим только по чанкам.** Вопрос не в том, правда ли это, а в том, следует ли это из найденных документов.

- Верно в реальном мире, но в чанках этого нет → **не поддержано**.
- Здравый смысл и общие знания не добавляем. Исключение — тривиальная арифметика над числами из чанка и переформулировка.
- Вопрос пользователя можно использовать, чтобы понять, о чём предложение: местоимения («It was founded in 2015»), эллипсис («Yes, on all plans»).

---

## 3. Фактическое или нет (`is_factual`)

**Не фактические** (пропускаются и ошибкой не считаются):
- приветствия и прощания: «Hi!», «Hope this helps!»;
- предложения помощи: «Let me know if you have other questions.»;
- вопросы к пользователю: «Would you like more details?»;
- связки без содержания: «Here is what I found:», «Let me explain.».

**Фактические**, даже если так не выглядят:
- «The documents don't mention X» — это утверждение о чанках;
- советы и инструкции, если они взяты из чанков: «You should contact support within 14 days»;
- хеджированные утверждения: «It usually takes about 3 days».

Сомневаешься — считай фактическим.

---

## 4. Статус предложения

| Статус | Когда |
|---|---|
| `supported` | хотя бы один чанк поддерживает предложение **в одиночку**, и ни один ему не противоречит |
| `supported_multi` | ни один чанк не поддерживает в одиночку, но вместе поддерживают: сравнение, «both», сумма из двух чанков |
| `contradicted` | хотя бы один чанк говорит что-то несовместимое (другое число, дата, сущность, противоположный факт), и ни один не поддерживает |
| `not_mentioned` | чанки об этом молчат, ни поодиночке, ни вместе не поддерживают |

Если один чанк поддерживает, а другой противоречит (например, старая и новая версия политики), ставь `supported`, перечисли оба чанка и поставь `unsure` с комментарием «conflict».

### Пограничные случаи

| Ситуация | Статус | Почему |
|---|---|---|
| Подтверждена только часть предложения («30 days, and files are encrypted») | `not_mentioned` (или `contradicted`, если другая часть противоречит) | предложение оценивается целиком |
| Предложение сильнее чанка: чанк «may», ответ «will»; потеряно условие («only on Pro») | `not_mentioned` | чанк этого не утверждает |
| Предложение слабее чанка: чанк «always», ответ «usually» | `supported` | следует из чанка |
| Арифметика: чанк «$10 per month», ответ «$120 per year» | `supported` | тривиальный вывод |
| Предложение со ссылкой `[2]`, но поддерживает его чанк `[3]` | `supported`, `chunks = [3]` | ссылку не проверяем, проверяем содержание |
| Верно по общим знаниям («Paris is the capital of France»), в чанках нет | `not_mentioned` | судим только по чанкам |
| Факт обрезан на границе чанка, а продолжение в соседнем чанке | `supported_multi` | ни один чанк не поддерживает в одиночку |
| Неточная формулировка, но смысл тот же («about 30 days» при «30 days») | `supported` | |
| Неточное число («about 40 days» при «30 days») | `contradicted` | |

## 5. Релевантность (`relevance`)

Оцениваем **только одно: насколько ответ отвечает на вопрос**. Не важно, верен ли ответ и есть ли нужное в чанках, это проверяют другие поля.

| Уровень | Определение |
|---|---|
| `does not address` | ответ на другой вопрос, общие слова, уход от темы |
| `partially addresses` | закрыта меньшая часть вопроса, или ответ слишком общий, чтобы им воспользоваться |
| `mostly addresses` | ответ по существу, но пропущена второстепенная часть или нужное уточнение |
| `fully addresses` | закрыты все части вопроса |

**Отказы:**
- **Полный отказ** («The documents don't contain information about this») → `relevance = полный отказ`, уровень не ставится. Правильность отказа определяется по `answerable`.
- **Частичный отказ** (отвечает на одну часть, про другую говорит, что информации нет) → уровень по закрытой части, обычно `partially` или `mostly`.

Ответ с выдуманными фактами, но по теме, может получить `fully addresses`.

---

## 6. Отвечаемость (`answerable`)

Смотрим только на чанки, не на ответ.

- **да** — в чанках есть ответ на все части вопроса;
- **частично** — есть ответ на основную часть, но не на всё;
- **нет** — в чанках нет ответа на основную часть вопроса.

Из этого получается проверка отказов: полный отказ при `answerable = нет` — правильное поведение, при `answerable = да` — ошибка.

---

## 7. Процесс

1. **Пилот**: 30–50 ответов размечают все разметчики, затем обсуждаем расхождения и правим этот гайд. Пилотные примеры в тестовый набор не входят.
2. **Основная разметка**: каждый ответ размечает один человек. **20% ответов размечают двое** независимо.
3. По двойной разметке считаем согласие (κ Коэна) отдельно по `status`, `relevance` и `answerable`. **Это потолок для любого судьи**: модель не может согласоваться с людьми лучше, чем люди между собой.
4. Расхождения в двойной разметке разбирает третий человек; его метка финальная.
5. Примеры с `unsure` просматриваются отдельно, перед заморозкой набора.
6. Набор замораживается с версией (`judge_test-v1`). После этого метки не меняются; найденные ошибки исправляются только в новой версии, и в отчёте указывается, на какой версии мерили.

---

## 8. Размер (предложение для обсуждения)

- **500 ответов** (≈ 2.5k предложений, ≈ 10k пар предложение × чанк) — разумный старт:
  - точность на уровне ответа при ~85% известна с точностью около ±3 п.п. (95% CI);
  - разница двух судей в 5 п.п. различима на парных данных, но не в 2 п.п.
- Если нужно сравнивать по отдельным срезам (продукт, длина ответа), а не только в целом, нужно 1000+.
- Выборка стратифицируется: обычные ответы, ответы, которые текущий LLM-судья счёл плохими, отказы, длинные ответы. Доли страт фиксируются заранее и указываются в отчёте.

## 9. Откуда данные

Формат выгрузки описан в `jevlite.judge.export`: одна строка на ответ, поля `question`, `chunks`, `answer` и вердикты текущего судьи в `llm_judge` (нужны для H0). Статистика длин считается сразу по выгрузке:

```bash
uv run python scripts/judge_length_stats.py --data data/judge_export.jsonl --out reports/judge_lengths
```
