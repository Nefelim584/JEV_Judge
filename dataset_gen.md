## 3. Конвейер

Каждый шаг пишет результат в SQLite (`data_gen/store.py`), поэтому прогон можно остановить и продолжить. Колонка «Кто» говорит, откуда метка: `program` или `teacher` (`dataset_dicr.md` 8.7).

| # | Шаг | Кто | Что получается |
|---|---|---|---|
| 1 | `taxonomy` | учитель, один раз | Темы по доменам (~150 на домен). Дедупликация и заморозка до планирования |
| 2 | `plan` | код | План каждого кейса: домен, тема, форматы и число чанков, вид и стиль вопроса, виды ответов и пертурбаций, сложность, сплит. **Модель не решает, какой кейс пишет** |
| 3 | `document` | учитель | Исходные документы (вымышленные организации и продукты). Один документ — на 4–5 кейсов (разные темы и аспекты одного документа) |
| 4 | `chunk` | код | Нарезка как у настоящего чанкера: обрывы, перекрытия, хлебные крошки (`dataset_dicr.md` 4.4) |
| 5 | `near_miss`, `unanswerable`, `conflict`, `near_duplicate` | **Haiku 5.5** | Трудные отвлекатели, неотвечаемые наборы, старые версии чанков, почти-дубли |
| 6 | `question` | **Haiku 5.5** | Вопрос по плану (вид, стиль, шаблон) |
| 7 | `answer` | учитель | Обоснованный ответ с цитатами из чанков |
| 8 | Другие ответы | учитель | `refusal`, `partial_refusal`, `off_topic`, `evasive`, `hallucinated` |
| 9 | `perturb` | **код**, где можно | `number_swap`, `date_swap`, `entity_swap`, `citation_swap` — значения из отвлекателей, метка известна по построению |
| 9b | `perturb` | **Haiku 5.5** | `unsupported_addition`, `negation`, `quantifier_scope`, `relation_flip`, `cross_chunk_merge` |
| 10 | `label` | учитель | Метки `supports / contradicts / silent`, **один вызов на чанк**, все ответы кейса сразу. Компактный JSON; цитата только для `supports` / `contradicts` |
| 11 | `verify` | учитель, другой промпт | Независимая вторая разметка тех же пар (раздел 6) |
| 12 | `label_full` | учитель, **только кейсы с 2+ relevant-чанками** | `supported_multi` (`dataset_dicr.md` 6.4). В остальных кейсах статус выводится кодом из меток по чанкам |
| 12b | `answerable` | **код** | По плану: неотвечаемый набор строится как неотвечаемый. Учитель проверяет только выборку |
| 13 | `filter` | код | Схема, цитаты, согласие `label` и `verify`, дедупликация (раздел 6) |
| 14 | `flatten` | код | Плоские записи `questions.jsonl` (`dataset_dicr.md` 2.3) и `mix`-совместимый формат |

Неизменённые предложения пертурбированного ответа **наследуют** метки исходного. Учитель размечает только новые предложения. Это главный способ экономии на шаге 10.

## 4. Учитель и вызовы

- **Клиент**: `anthropic` SDK, `AnthropicBedrockMantle(aws_region=...)`. В `data_gen/llm.py` появляется второй бэкенд рядом с llama-server; выбор в `config.yaml` (`llm.backend: bedrock | llama`).
- **Thinking выключен** на всех шагах, кроме `taxonomy` и арбитра (раздел 6). На Sonnet 5.5 `{type: "disabled"}` даёт 400; выключается через `thinking: {type: "between_tools"}` при `effort` не выше `high`. Thinking-токены оплачиваются как выход, а на коротких структурированных ответах почти ничего не дают. Проверяем на смоуке: разметка с thinking и без на одних и тех же кейсах.
- **Haiku 5.5** (если он проверяющий): thinking по умолчанию включён, `effort: low`; цена $0.10 / $0.50 за 1M при промпте до 100k токенов.
- **Sampling-параметры не передаём.** Sonnet 5.5 отклоняет нестандартные `temperature` / `top_p` / `top_k`, а с 2026-10-21 они дают 400 на всех моделях. Раздел `sampling` в `config.yaml` заменяется на `max_tokens` по шагам. Разнообразие даёт план (шаг 2): тема, аспект, форматы, стиль, плюс случайное «зерно» в промпте (`variant: 7 of 20`).
- **Structured outputs** (`output_config.format`, JSON schema из `data_gen/schemas.py`): ответ всегда валиден по схеме, повторов из-за битого JSON нет.
- **Повторы**: транспортные ошибки и 429 — SDK; провал проверки кода (цитаты нет в чанке, не та длина) — до `max_attempts: 3` с другим зерном.
- **Логи**: на каждый вызов в SQLite пишутся модель, шаг, токены входа и выхода, время. Отчёт о стоимости строится из них.

## 5. Batch на Bedrock

- Batch-режим Bedrock (`CreateModelInvocationJob`): JSONL с запросами в S3 → JSONL с ответами в S3. Дешевле on-demand примерно вдвое (цену сверить на странице Bedrock перед запуском). Batches API от Anthropic на Bedrock **не работает**, это другой механизм.
- Шаги зависят друг от друга, поэтому batch идёт **волнами по шагам**: все `document` → все `near_miss` и `question` → все `answer` → … → `verify`. Каждая волна — один или несколько job, результаты загружаются в SQLite, затем код готовит следующую волну.
- **Смоук и отладка — on-demand**: быстрее цикл, объём маленький.
- Prompt caching (чанки кейса повторяются в `label`, `verify`, `label_full`) включаем, если Bedrock применяет его в batch-режиме. Не применяет — экономия только на on-demand. Проверяем на смоуке.

## 6. Проверки качества

**Код, на каждой записи:**
- валидность по схеме, длины в пределах плана;
- каждая цитата из `label` / `verify` **дословно** есть в чанке (`data_gen/checks.py`);
- пертурбированное предложение отличается от исходного и по длине укладывается в `length_ratio`;
- почти-дубли документов (MinHash, Jaccard 0.6) удаляются до нарезки.

**Согласие разметок.** Пара (предложение, чанк) остаётся, только если `label` и `verify` дали одну метку. Ответ выбрасывается, если:
- разметки расходятся хотя бы на одной паре, размеченной учителем;
- метка противоречит построению (обоснованное предложение не поддержано, пертурбированное всё ещё поддержано).

**Кто проверяет — решаем на смоуке.** Два варианта:

| | **V1. Sonnet 5.5, другой промпт** | **V2. Haiku 5.5 + арбитр** |
|---|---|---|
| Независимость | Низкая: общие слепые пятна Sonnet (например, «верно в мире» за поддержку, мягкость к перефразу) проходят фильтр и становятся систематической ошибкой меток | Выше: модель другого размера ошибается в других местах. Не полная — та же линейка моделей |
| Что выбрасывается | Мало | Haiku слабее, поэтому чаще не соглашается на **трудных** парах (сильный перефраз, `quantifier_scope`, два чанка). Если просто выбрасывать — датасет становится легче. Поэтому при расхождении не выбрасываем сразу, а зовём **арбитра**: Sonnet 5.5 с thinking. Пара остаётся, если арбитр согласен с `label` |
| Цена проверки на 1k кейсов (batch) | ~$8 | ~$7 (Haiku почти бесплатен, основное — арбитр на Sonnet: один вызов на чанк со спорными предложениями) |

Как выбираем: на 200 кейсах смоука прогоняем оба варианта и вручную размечаем ~200 пар (с перекосом в трудные). Смотрим (1) точность итоговых меток против ручных, (2) долю выброшенного по сложности (`easy / medium / hard`). Если V2 не хуже по точности и не вычищает `hard` — берём V2. По цене варианты почти равны, решает качество.

**Датасет целиком** (отчёт `quality_report.md`):
- доля согласия `label` / `verify` по шагам, доменам, видам пертурбаций; доля выброшенного;
- распределения меток, видов ответов и пертурбаций против плана (`dataset_dicr.md` 6, 11);
- **короткие пути**: hypothesis-only (модель без чанка ≈ случайная), passage-swap 2×2, лексическое пересечение как единственный признак, позиция искажения;
- **ручное чтение** 200 случайных кейсов до обучения (и 100 после каждой правки промптов).

## 7. Длинные состояния для Stage C

Длинные состояния **собираются кодом** из размеченных кейсов части A. Новых документов учитель для этого не пишет, поэтому часть B стоит копейки.

- **Сборка**: чанки кейса (relevant + hard negatives) + отвлекатели из **других тем** до нужной длины. Корзины длины: 1–2k, 2–4k, 4–8k токенов ModernBERT.
- **Позиция доказательства**: relevant-чанки ставятся в начало, середину или конец (по трети). Позиция пишется в `meta` для отчёта по позициям (`todo.md` 2.11).
- **Метки наследуются**: статус предложения по набору не меняется от добавления отвлекателей из чужих тем с вымышленными сущностями — они `silent` по построению.
- **Проверка наследования**: на выборке 300 групп учитель делает `label_full` по всему длинному состоянию. Расхождение больше 3% — пересматриваем подбор отвлекателей (например, только другой домен).
- **Утверждения на два далёких чанка**: кейсы из `dataset_dicr.md` 6.4 собираются так, чтобы два нужных чанка оказались далеко друг от друга.
- Сплиты те же, что у исходных кейсов, отвлекатели берутся только из того же сплита.

Это предлагаемое дополнение к `dataset_dicr.md` (раздел 4.2 сейчас ограничивает `faithfulness_full` до «обычно 1–3k»).

## 8. Домен нашей системы

Наша система: пользователи задают вопросы по **спецификациям FIX и REST API**, ассистент отвечает по найденным чанкам, судья проверяет ответ. С jev-lite судить можно в реальном времени, поэтому важна и латентность (Phase 9).

**Чем домен особенный:**
- **Стандартный FIX известен всем LLM** и попал в предобучение. Ответ «верный по стандарту FIX, но в чанке этого нет» должен быть `silent` (`dataset_dicr.md` 8.1). Значит, нужно много документов, где правила **отличаются от стандарта**: свои теги (5000+), свои обязательные поля, свои значения перечислений, ограничения конкретной площадки.
- Что легко исказить: номера тегов и их имена, допустимые значения (`OrdType`, `TimeInForce`, `Side`), обязательность поля, тип сообщения (`35=D` vs `35=G`), порядок в сессии (Logon, Heartbeat, ResendRequest); у REST — метод и путь, параметры и их типы, значения по умолчанию, коды ответа, лимиты запросов, версии API, формат авторизации.
- Форматы чанков: таблицы полей (`Tag | Name | Req | Description`), примеры сообщений `8=FIX.4.4|9=…|35=D|…`, JSON-примеры запросов и ответов, описания эндпоинтов. В `config.yaml` доля `table` и `code_config` для этого домена выше, чем в среднем.

**Два источника, реальных документов — минимум:**

| Источник | Как | Доля кейсов домена |
|---|---|---|
| **C1. Вымышленные спецификации** | Sonnet пишет спецификации вымышленных площадок и API по описанию домена и **по образцу** нескольких реальных разделов: та же структура, другие теги, поля, значения, правила | ~80% |
| **C2. Реальные разделы** | Небольшой набор разделов нашей спецификации, нарезанный **нашим** чанкером; учитель пишет вопросы, ответы и пертурбации | ~20%, не больше нескольких сотен чанков |

**Отделение от человеческого теста (Phase 11).** Человеческий тест будет на вопросах к той же спецификации, поэтому:
- до генерации разделы спецификации делятся на «для генерации» и «для теста»; C2 берёт только первые;
- список разделов для теста замораживается и хранится рядом с тестом;
- в отчёте Phase 11 метрики считаются отдельно по тестовым вопросам, чьи чанки ни разу не попали в C2.

Домен называется `trading_api` с подвидами `fix` и `rest` (поле `meta.subdomain`). Вес в плане — около 20% кейсов каждой волны, поровну FIX и REST. В `test_ood` домен не уходит; его OOD-проверка — человеческий тест.

## 10. Объёмы и смета

**Бюджет: не больше $600 вместе с запасом.** Под него конвейер экономный (раздел 3):
- Sonnet 5.5 только там, где решается качество: документы, ответы, разметка, `label_full`, арбитр;
- Haiku 5.5 на простых шагах (отвлекатели, вопросы, пертурбации) и на `verify` (вариант V2, раздел 6);
- один документ на 4–5 кейсов; компактный вывод разметки; `label_full` только там, где он нужен; `answerable` — кодом.

Оценка на один кейс (до смоука; смоук даёт точные числа из логов). Batch: Sonnet 5.5 $1 / $5 за 1M, Haiku 5.5 $0.05 / $0.25.

Правила, чтобы не выйти за лимит:
- **После смоука пересчитываем** стоимость кейса по логам и подбираем размер волн так, чтобы итог с запасом был ≤ $600. Если кейс дешевле оценки — волны до 8–10k.
- **Волна 2 — только если** волна 1 дала прирост на коротком дообучении; иначе останавливаемся (~$275 всего).
- **AWS Budgets**: алерт на $400 и $550 по Bedrock.
- Генератор пишет стоимость каждого вызова в SQLite; batch-волна не стартует, если вместе с уже потраченным она выходит за лимит.

**Вариант 20k кейсов** (2 × 10k). При $0.033 за кейс это ~$705, лимит превышен. Влезть можно только с дополнительной экономией:
- `refusal`, `partial_refusal`, `off_topic`, `evasive` пишет Haiku; Sonnet пишет только обоснованный ответ (−$0.003 на кейс);
- один документ на 6–8 кейсов (−$0.002; разнообразия меньше);
- запас на повторы 10% вместо 20%, если смоук покажет, что повторов мало (−$0.0025).

Тогда ~$0.025 за кейс → 20k ≈ $500 + смоук и проверки ≈ **$545**, запас ~$55 (≈ 10%). Решаем после смоука по реальной стоимости кейса; стоп по бюджету (выше) в любом случае не даст выйти за $600 — в худшем случае волна 2 будет меньше 10k.

Для сравнения, полный вариант без экономии (Sonnet на всех шагах, 2 × 10k) — ~$1 350, с запасом ~$1 750. Первая прикидка ~$470 была грубой оценкой «на глаз» (200M токенов) и не учитывала двойную разметку каждой пары.

## 11. Порядок работ

1. **Код** (без затрат; учёт стоимости и стоп по бюджету — сразу): Bedrock-бэкенд в `data_gen/llm.py`, шаги конвейера, batch-волны, `filter`, `flatten`, тесты на заготовленных ответах. Домен `trading_api` в `config.yaml`; деление разделов спецификации на «генерация / тест».
2. **Смоук 200 кейсов**, on-demand, оба варианта проверки. Читаем все 200 руками, размечаем ~200 пар, считаем стоимость кейса из логов. Правим промпты; повторяем, пока не устроит. Выбираем V1 или V2.
3. **Волна 1: ~7k** (по смете после смоука), batch. Отчёт качества, проверки коротких путей, ручное чтение 200. Короткое дообучение (Stage B + волна 1): даёт ли синтетика прирост на `test_ood` и на срезе `trading_api`.
4. **Правки по итогам волны 1** (промпты, доли в плане). Изменения записываются; версия датасета `jud-v1` → волна 2 пишет `jud-v1.1`.
5. **Волна 2: ~7k**, batch, на исправленных промптах — только если волна 1 дала прирост. Тестовые сплиты волны 1 **не пересобираются**: волна 2 добавляет кейсы в те же сплиты по тем же правилам, тест волны 1 остаётся замороженным для сравнения. Две волны заодно дают две точки кривой обучения (H1).
6. **Часть B**, сборка кодом и проверка наследования.
7. Публикация датасета там, где идёт обучение (раздел 9), микс `stage_c.yaml`.
